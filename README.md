# Motor Insurance Policy Assistant

Question answering over **36 public Indian motor insurance policy documents from 10 insurers**
(private car, two-wheeler and goods-carrying vehicle wordings, add-ons and customer information sheets).
Every answer cites the clause and page it comes from, and the assistant says so when the documents don't cover a question.

The project is built around **measurement**: a labeled eval set and a held-out set drove every retrieval decision,
and each change below is kept or dropped based on its numbers.

```
question ─► insurer detection ─► hybrid search (BM25 + embeddings, RRF) ─► cross-encoder rerank ─► LLM answer with [n] citations
                                        │
               agent mode ─► tool-calling loop ─┬─ search_policy_clauses
                                                ├─ compare_clauses   ─► Neo4j: Concept → Chunks per insurer/vehicle ─► rerank
                                                ├─ follow_references ─► Neo4j: "subject to IMT 22" → the clause that defines it
                                                └─ get_section / list_insurers
```

## Results

### Retrieval: recall@5 (did a chunk containing the labeled evidence come back in the top 5?)

| Setup | Hand-written set (29 answerable) | **Held-out set (60, never tuned on)** |
|---|---|---|
| BM25 | 79.3% | 53.3% |
| Dense embeddings (bge-small) | 69.0% | 61.7% |
| Hybrid (RRF) | 74.1% | 75.0% |
| Hybrid + cross-encoder rerank | 86.2% | 86.7% |
| **Hybrid + rerank + insurer filter** (production) | **91.4%** (MRR 0.80) | **86.7%** (MRR 0.70) |

The hand-written set was used while tuning, so its numbers are optimistic; the held-out set is the honest one.
The held-out questions were generated by an LLM from randomly sampled chunks (fixed seed), kept only if their evidence
is verbatim in the source, then spot-checked by hand (10 of 12 sampled were clean; one mislabeled question was fixed).

### What moved retrieval (hybrid + rerank, one change at a time, hand-written set; each row includes the ones above)

| Change | recall@5 | Why |
|---|---|---|
| Baseline: 1,200-char chunks, no filter | 29.3% | |
| Fairer labels (same clause, same insurer, any of its documents) | 39.7% | insurers repeat clauses across their own documents |
| Insurer filter from names in the question | 48.3% | many insurers share identical tariff wording, so unfiltered search found the right clause from the wrong insurer |
| 700-char chunks with 200-char overlap | 72.4% | big chunks mixed several clauses; overlap keeps boundary sentences whole |
| Drop repeated page headers | 62.1% ▼ | the headers had been carrying *which product* a chunk belonged to |
| **Contextual chunk headers** (index "insurer \| product \| section" with each chunk) | **89.7%** | restores that context consistently for every chunk |
| Domain synonyms for BM25 and the reranker ("drunk" → "intoxicating liquor") | 91.4% | small gain; none on the held-out set |

### Answers (35 hand-written questions; answers by gpt-oss-120b, graded by gpt-oss-20b)

| Metric | Single search | Agent (partial: 7 questions so far) |
|---|---|---|
| Correct (agrees with reference) | 89.7% | 6 / 6 answerable |
| Faithful (every claim supported by the excerpts) | 96.6% | 6 / 6 |
| Citation accuracy (cited chunk contains the evidence) | 89.7% | 75% |
| Correct refusals on unanswerable questions | 6 / 6 | 1 / 1 |
| Wrong refusals on answerable questions | 0 / 29 | 0 / 6 |
| **Comparison questions correct** | **2 / 4** | **4 / 4** |
| Tokens per question | ~1,440 | ~13,200 |
| Latency per question | ~5.6 s | ~81 s |

All three single-search failures are the same case: Universal Sompo has a base-policy towing limit
("Rs. 1500 per accident") *and* a towing add-on ("free within 50 km"); search returned both and the model answered
from the add-on. The agent searches each side separately and gets these right, at about 9x the tokens.

On the one unanswerable question in the agent sample ("premium for a Honda City"), the agent searched six times and
used ~27k tokens before correctly refusing: agents cost the most when the answer doesn't exist.

**Still to measure:** the agent on the remaining 28 questions, and an ablation with and without the Neo4j tools
(in the 7-question sample the agent used the graph tool once, on the one comparison single search refused).
The Groq free tier allows 200k tokens per model per day, so these runs are done in parts and combined with
`python -m motor_rag.evaluate merge`.

## Things that went wrong and what they taught

- **Two-column PDFs.** Reading pages line by line merged "Definitions" with "Coverage". Blocks are now ordered column by column.
- **Truncated downloads.** A slow connection cut PDFs short; PyMuPDF silently repaired them and extracted garbled text
  ("wil", "acidental"). The downloader now checks `Content-Length` and rejects repaired files.
- **Table cells as headings.** A branch-office table turned city names into 800+ junk sections. Runs of tiny blocks are now table rows.
- **Stale embedding cache.** Keyed on chunk ids, it could reuse old vectors after re-chunking. Now keyed on a hash of the indexed text.
- **Citation format.** `gpt-oss` writes `【1】`, not `[1]`; citation accuracy looked like 31% until the parser was fixed.
- **Retired model.** `llama-3.3-70b-versatile` was no longer on Groq; the model is configured in `.env`.

## Agent harness

`src/motor_rag/agent.py` runs the tool-calling loop and keeps it safe:
step limit (6) with a forced final answer, tool arguments validated (bad calls return an error the model can correct),
identical repeat calls served from cache, one global numbering for every excerpt so `[n]` always means one chunk,
and a per-step trace (tool, arguments, duration) returned by the API. Graph tools are offered only when Neo4j is reachable.

## Clause graph (Neo4j)

`(:Insurer)-[:PUBLISHES]->(:Document)-[:HAS_SECTION]->(:Section)-[:HAS_CHUNK]->(:Chunk)`, plus
`(:Chunk)-[:MENTIONS]->(:Concept)` for 26 insurance concepts, `(:Chunk)-[:DEFINES|REFERS_TO]->(:Clause)` for
IMT endorsements and policy sections, and `(:Chunk)-[:NEXT]->(:Chunk)` for reading order.
Built with rules, not an LLM, so it is reproducible: 5,643 chunks, 394 clauses, 471 definitions, 390 resolved references.

## Run it

```bash
uv sync                                    # Python 3.12; installs CPU PyTorch on Linux
cp .env.example .env                       # add a free Groq key from console.groq.com/keys
uv run python -m motor_rag.download        # PDFs come from insurer websites; they are not committed
uv run python -m motor_rag.ingest
docker compose up -d                       # Neo4j (optional; the agent works without the graph tools)
uv run python -m motor_rag.graph build
uv run uvicorn motor_rag.api:app --port 8000   # chat page at http://localhost:8000

uv run pytest -q                                            # 34 unit tests, no network or API key
uv run python -m motor_rag.evaluate retrieval --set heldout # no API key needed
uv run python -m motor_rag.evaluate answers [--agent]       # needs GROQ_API_KEY
```

Some insurer sites (Acko, Generali) refuse automated downloads; those rows in `data/sources.csv` can be saved
by hand into `data/raw/<doc_id>.pdf`.

## Limitations

- 36 documents from 10 insurers; not every product or the latest version of every wording.
- Concept tagging is keyword rules, so it misses paraphrases the rules don't list.
- The cross-encoder adds ~2.5 s per query on CPU.
- Not insurance advice: the policy schedule and the insurer's current wording always govern.
